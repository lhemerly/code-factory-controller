# OpenCode V2 external execution and controller authority

The explicit `opencode_v2` mode makes OpenCode 2.0.29 and its pstack adapter responsible for coding execution. Code Factory retains approved jobs, worktrees, attempt/lease limits, scoped worker capabilities, independent verification, integration, delivery and conservative recovery. This mode does not dispatch prompts, choose models, retry inference, enumerate a work backlog or introduce another scheduler. Existing V1 and llama.cpp modes remain available for their existing users.

Use a dedicated, explicitly approved loopback V2 server and a reviewed controller configuration with `opencode_url` set to its origin. Keep the existing explicit free-model allowlist, zero-spend ceiling and data approval. Changing an existing database's configuration remains prohibited; use a separate reviewed configuration/data directory. Do not put the controller operator credential in the worker runtime environment. `FACTORY_OPENCODE_PASSWORD`, if supplied to the controller by the host, authenticates native observation only; this integration does not provision credentials or install a service.

The host admits a bounded job and calls `prepare` with mode `opencode_v2`. It creates the native session in that attempt's exact prepared worktree without inference, then calls operator `bind-v2` with `job_id`, `session_id` and a private worker capability. Ordinary `bind` refuses V2 attempts. The observed native session's identity, native project, exact location, parent and complete metadata are persisted immutably for that attempt. No controller/native project-ID equivalence is assumed: their separate identities are explicitly bound. The worker capability remains limited to that job and actual executing session.

The pstack bridge uses the existing four worker operations and deterministic request identities. V2 status additionally exposes `execution_policy`: mode, approved models, free-only flag, zero spend ceiling, supported runtime and unsupported delegation. The plugin never receives operator authority. Workflow prose, native `succeeded` outcomes and model-authored ledger strings cannot stand in for a controller receipt.

## Native observations and refusal conditions

Before a new worker mutation, the controller independently checks the pinned V2 version, current scope/ownership, known zero cost, complete nonnegative usage, approved model identities and bounded complete native session/transcript observations. An absent model is allowed only for deterministic sessions with known zero tokens. Assistant/compaction usage must be known; unsupported or unmeasured records fail closed. This is an observation of runtime accounting and an approved free-model policy, not independent measurement of provider invoices. The plugin separately checks current native model prices before requests.

Candidate verification, integration and delivery additionally require no active native drain, no pending inbox items, terminal known tool/shell/compaction records, and no running native shell at the prepared location. The initial slice refuses every descendant session, including a moved child found in the complete server-wide session inventory. Pagination is bounded to 32 pages of 100 sessions; incomplete, inconsistent or unavailable observations block effects. Each observation has a 30-second total deadline and bounded response/transcript sizes. Export and repeated session reads must agree on ownership, accounting and update identity.

The official 2.0.29 contracts used here are `/api/info`, `/api/session`, `/api/session/{id}`, `/api/session/active`, `/api/session/{id}/inbox`, `/api/experimental/session/{id}/export` and `/api/shell`. V2 abort first durably blocks the job, expires its lease and journals stop intent, before waiting for an in-flight controller effect or making any native request. Concurrent acceptance cannot save a stale revision. It then validates pinned native ownership before `POST /api/session/{id}/interrupt?resume=false` and obtains a complete, consistent native execution-stop observation. There is no V1 abort fallback. An unbound or uncertain session requires explicit host inspection and binding before a stop can be established.

Execution stop and accounting settlement are separate results. Native version/scope/ownership, complete session inventory with no descendants, no active drain, an empty inbox, no running native shells and terminal known assistant/tool/shell/compaction records are required to confirm the stop. Active, missing or unknown execution observations keep it unconfirmed. Accounting fields do not replace those checks, and missing accounting does not turn an otherwise proven native stop into an execution failure.

`status.execution_recovery` exposes attempt/session/stop identity, the durable fence time, `execution_stop` and `accounting`. Stop intent, confirmation or failure survives restart in the existing private SQLite `metadata` table, using attempt-scoped `opencode-v2-recovery:<attempt>` and individual `opencode-v2-stop:<stop>` records. No database/configuration schema migration or automatic retry occurs. Confirmation includes the observed native identity/update, bounded inventory count and exported transcript SHA-256. Accounting preserves actual cost/tokens/model fields and explicit missing-field issues; message text and credential values are not copied into the recovery record.

Accounting is `settled_zero` only when the observed session and all model-bearing execution records provide complete, valid usage and comply with the existing approved-model/zero-spend policy. Here `settled_zero` means **zero spend**, not zero tokens: approved free-model execution may use positive measured tokens. Missing cost/tokens/model evidence remains `unknown`; known nonzero spend or an unapproved model is `violating`. Unobserved accounting after an incomplete stop is labeled `unobserved`. No missing field is replaced by zero, including a terminal provider HTTP403 with unmeasured assistant usage and initialized zero session aggregates.

A confirmed native stop can therefore return a blocked job with `dispatch_state: execution_stopped` and unknown/violating accounting. This is a successful stop observation, not accepted work, complete accounting or permission to reassign. Acceptance and requeue remain fenced. Only confirmed stop plus `settled_zero` accounting yields `dispatch_state: resolved`, after which the operator may requeue subject to existing attempt/integration limits. A failed interrupt, incomplete stop, unresolved descendant, pending inbox or lost server remains `stop_unconfirmed` (or `stop_pending` after interruption of the controller request). Later recovery still requires fresh native evidence; the controller offers no accounting override or inferred-zero fallback.

These are point-in-time native observations in a trusted dedicated runtime. They do not freeze native state atomically across HTTP requests, prevent a separately authorized host from resuming execution afterward, or establish kernel quiescence for arbitrary detached worker processes. No claim of arbitrary-process containment, full provider-spend enforcement or unattended readiness follows. Native descendants are deliberately unsupported rather than treated as quiet. Existing independent verifier child ownership, pidfd/subreaper supervision, immutable receipts, artifact digests and restart fences remain unchanged.

## Verification

`tests/opencode_v2.rs` uses mocked V2 HTTP responses and the actual controller verifier to exercise candidate verification, integrated verification and archive delivery without inference. It covers binding scope, native ownership/runtime changes, unknown/nonzero cost and models, active/queued/tool/shell/descendant/pagination uncertainty, failed abort/requeue, forged receipt rejection and controller restart. Recovery regressions exercise terminal HTTP403 with missing usage, separate unknown/violating accounting, an abort racing an actual in-flight pre-integration quiet check, and cancelled-abort restart with no replay. These mocked observations do not establish live OpenCode compatibility; the pstack package's separate isolated native integration test supplies that evidence. Run the existing controller Rust and Python suites as regression checks, including all verifier lifecycle/recovery tests. Historical failed live runs and their databases are not upgraded or rewritten by these tests.
